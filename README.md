# Givana Rewards System

## Overview

Givana is a decentralized finance (DeFi) application built on Solana that allows users to stake JitoSOL to earn yield. A key feature of Givana is enabling users to donate a portion of their earned yield to selected Non-Governmental Organizations (NGOs) seamlessly. This document outlines the evolution of its reward distribution mechanism.

## Previous Reward System Implementation (Pre-Refactor)

### Core Logic

The earlier version of the Givana rewards system was based on the following principles:

1.  **Global Weighted Donation Rate:** A system-wide `weighted_donation_rate` was calculated based on all users' stakes and their individual donation percentages. This rate represented an average donation preference across the platform.
2.  **Immediate Reward Splitting:** When new rewards (e.g., from Jito Vaults) entered the system, they were immediately split into a "user portion" and an "NGO portion" using this global `weighted_donation_rate`.
3.  **Separate Global Accumulators:**
    *   `acc_reward_per_share`: Accumulated the "user portion" of rewards per unit of gSOL.
    *   `acc_ngo_donation_per_share`: Accumulated the "NGO portion" of rewards per unit of gSOL.
4.  **User and NGO Checkpoints:**
    *   `UserAccount` stored `last_reward_checkpoint` (for their share) and `last_ngo_donation_checkpoint` (for the NGO share they "generated" based on global rate).
    *   `NGOAccount` stored `last_ngo_checkpoint` to track its claims from the global NGO pot.
5.  **NGO Reward Distribution:** A separate instruction, `DistributeNgoRewards`, (often admin-triggered) was used to calculate each NGO's share from the global `acc_ngo_donation_per_share` based on an estimated `ngo_weight` (derived from `total_users_donating` and the `weighted_donation_rate`). This would update the NGO's `pending_rewards`.

### Limitations

This approach had several drawbacks:

1.  **Imprecision for Individual Donations:** The primary issue was the use of a global `weighted_donation_rate`. If a user specified a 5% donation, but the global average was (for example) 20%, their stake's contribution to the "user portion" and "NGO portion" was based on this 20% average, not their specific 5%. This meant:
    *   Users wanting to donate less might have more of their generated yield allocated to the global NGO pool than they intended.
    *   Users wanting to donate more might have less of their generated yield allocated to the global NGO pool.
2.  **Fairness Concerns:** The averaging mechanism could lead to situations where users who preferred lower donation rates effectively subsidized the donations of those who preferred higher rates, or vice-versa, in terms of how the initial reward pool was split.
3.  **Complexity:** Managing multiple global accumulators tied to an averaged rate, plus a separate distribution step for NGOs, added complexity to the system logic.
4.  **Delayed NGO Crediting:** NGOs wouldn't see their exact accruals in real-time from specific users; they had to wait for the `DistributeNgoRewards` process.

## New (Current) Reward System Implementation

To address the limitations of the previous system, a significant refactor was undertaken, resulting in a more precise, fair, and efficient mechanism.

### Core Logic

The new system operates as follows:

1.  **Single Global Yield Accumulator:**
    *   A single global accumulator, `GlobalState.acc_total_yield_per_gsol`, tracks the total gross rewards earned per staked gSOL token *before* any donation considerations.
    *   When new rewards `R_new` enter the system, `acc_total_yield_per_gsol` is updated by `(R_new * PRECISION_FACTOR) / total_gsol_supply`.

2.  **Just-in-Time (JIT) Per-User Reward Calculation:**
    *   A core internal function, `update_user_rewards_and_credit_ngo`, is called whenever a user's reward-bearing state needs to be updated (e.g., before a deposit, claim, or change in donation settings).
    *   This function calculates the gross rewards generated by that specific user's stake since their last update by comparing their `last_total_yield_checkpoint` with the current `global_state.acc_total_yield_per_gsol`.

3.  **Individual Donation Percentage Application:**
    *   The user's chosen `donation_rate` (stored in their `UserAccount`) is applied to *their* calculated gross rewards.
    *   `total_rewards_by_user = (user_gsol_balance * (global_accumulator - user_checkpoint)) / PRECISION_FACTOR`
    *   `ngo_share = (total_rewards_by_user * user_donation_rate_basis_points) / 10000`
    *   `staker_share = total_rewards_by_user - ngo_share`

4.  **Direct NGO Crediting:**
    *   The calculated `ngo_share` is immediately added to the `pending_claimable_donations` field in the specific `NGOAccount` designated by the user's `ngo_address`.
    *   The `staker_share` is added to the `pending_rewards` field in the `UserAccount`.

5.  **Simplified User State:**
    *   `UserAccount` now only stores `last_total_yield_checkpoint`. Fields like `last_ngo_donation_checkpoint` and `pending_ngo_donation` (which was for the user's view of NGO share) are removed.

6.  **Obsolete Components Removed:**
    *   `GlobalState.weighted_donation_rate` and `GlobalState.acc_ngo_donation_per_share`.
    *   The `DistributeNgoRewards` instruction.
    *   The `ProcessRewards` instruction (as updates are now JIT).

### How It Solves Previous Issues

1.  **Precision:** Each user's donation is an exact percentage of the rewards *their specific stake* generated.
2.  **Fairness:** The global averaging issue is eliminated. Rewards are calculated per user first, then split.
3.  **Simplicity:** The overall logic is simpler with a single primary yield accumulator and direct application of user preferences.
4.  **Real-Time NGO Accrual:** NGOs' `pending_claimable_donations` are updated as soon as any donating user's rewards are processed, providing a more current view of their available funds.

### Pros

*   **Accuracy & Fairness:** Donations precisely match individual user intent.
*   **Efficiency:** Core reward input is O(1) (updates one global accumulator). User-specific calculations are also O(1) and only performed when needed (JIT). No iteration over users or NGOs for global reward processing.
*   **Transparency:** Easier to understand how rewards are generated and split for each user.
*   **Alignment with Standard DeFi Patterns:** The use of a global yield accumulator and per-user checkpoints/updates is a common and well-understood pattern in yield farming (similar to MasterChef-like systems in principle).

### Cons, Limitations, and Edge Cases

1.  **Integer Truncation:** For users with very small gSOL balances or during periods of very low yield, the calculated rewards (`total_rewards_generated_by_stake` or `ngo_donation_amount`) might truncate to zero after division by `PRECISION_FACTOR`. This is a standard trade-off in fixed-point arithmetic.
2.  **Client-Side Responsibility for NGO Accounts:** When users claim rewards or their state is updated, the instructions often require the user's chosen `NGOAccount` to be provided if a donation is applicable. Clients (UIs/scripts) must correctly fetch and include this account in the transaction. Failure to do so (or providing the wrong one) can lead to:
    *   The NGO donation portion for that period not being credited if the NGO account isn't available to the `update_user_rewards_and_credit_ngo` function. These "stuck" rewards would remain in the main reward pool token account.
    *   Transaction failure if an incorrect NGO account (not matching `user_account.ngo_address`) is passed to an instruction that validates it (e.g., `ClaimStakerRewards`).
3.  **Changing NGOs:** The `set_donation_rate_and_address` instruction currently returns an error (`ChangingNgoNotSupportedDirectly`) if a user tries to change from one NGO to another directly. This is because the instruction isn't set up to load the accounts for *both* the old and new NGO to settle rewards accurately. A user would need to potentially call a "settle" instruction or the client would make multiple calls, or this instruction could be enhanced in the future.
4.  **`withdraw.rs` Refactor Needed:** The `withdraw.rs` file (and associated withdrawal logic) was identified as still using some of the old, now-removed state fields and accumulators. It requires a separate refactoring effort to align with the new rewards system. Until then, withdrawals might not correctly account for or settle a user's pending rewards.
5.  **Max Value for Accumulators:** Global accumulators and user checkpoints are large numbers (`u64`). While sufficient for a very long time, they are not infinite and could theoretically reach their maximum value in extreme long-term scenarios with continuous high rewards.

## Mathematical Outline of New Reward Calculation

Let:
*   `G_u`: gSOL balance of user `u`.
*   `D_u%`: Donation percentage chosen by user `u`.
*   `D_u_bp`: Donation rate in basis points (e.g., for 5%, `D_u_bp = 500`).
*   `A_global`: Current value of `global_state.acc_total_yield_per_gsol`.
*   `A_user_prev`: Value of `user_account.last_total_yield_checkpoint` (user's snapshot of `A_global` from their last update).
*   `P`: `PRECISION_FACTOR` used for scaling.

**1. Global Reward Update (when `R_new` rewards arrive):**
   `ΔA_global = (R_new * P) / total_gsol_supply_overall`
   `A_global_new = A_global_old + ΔA_global`

**2. User-Specific Reward Calculation (via `update_user_rewards_and_credit_ngo`):**
   a.  **Yield Delta for User:**
       `ΔA_user = A_global_current - A_user_prev`

   b.  **Gross Rewards Generated by User's Stake:**
       `R_total_gen_u = (G_u * ΔA_user) / P`

   c.  **Split Rewards:**
       `R_ngo_u = (R_total_gen_u * D_u_bp) / 10000`
       `R_staker_u = R_total_gen_u - R_ngo_u`

   d.  **Update Pending Balances:**
       `user_account.pending_rewards += R_staker_u`
       `ngo_account.pending_claimable_donations += R_ngo_u` (if NGO is set and valid)

   e.  **Update User's Checkpoint:**
       `user_account.last_total_yield_checkpoint = A_global_current`

This revised system provides a robust and fair mechanism for distributing rewards in Givana.
